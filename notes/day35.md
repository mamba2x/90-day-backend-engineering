# Day 35: FastAPI + SQLAlchemy Database Integration

## Summary

Today I connected my FastAPI Task API to a real SQLite database using SQLAlchemy. Before this, the application relied on a normal Python list to store task data, which meant all the information would disappear whenever the application stopped running. By introducing SQLite and SQLAlchemy, the task data can now be stored persistently in a database file and retrieved again even after the FastAPI server restarts.

I started by configuring the database connection using a SQLite database URL and a SQLAlchemy engine. I also used the SQLite-specific `check_same_thread=False` option so the database connection can work correctly with FastAPI's request handling. After that, I created a SQLAlchemy `DeclarativeBase` and defined the `Task` ORM model with fields for the task ID, title, completion status and priority. I also used `Base.metadata.create_all(engine)` to ensure that the required database table exists before the application starts interacting with it.

One of the main things I understood today was the difference between a SQLAlchemy ORM model and a Pydantic model. The SQLAlchemy `Task` model represents the actual database table and the rows stored inside it, while the Pydantic models are responsible for validating data coming into the API and controlling the shape of data returned to the client. I created a request model for creating tasks and a response model for sending task information back through FastAPI.

I also learned how `ConfigDict(from_attributes=True)` is used in the Pydantic response model. Since SQLAlchemy returns ORM objects rather than normal dictionaries, Pydantic needs permission to read values directly from object attributes such as `task.id`, `task.title`, `task.completed` and `task.priority`. Using `from_attributes=True` allows FastAPI to convert SQLAlchemy ORM objects into proper JSON responses.

Another major part of today's work was creating a reusable SQLAlchemy Session dependency for FastAPI. Instead of manually creating a database Session inside every route, I created a `get_session()` dependency and injected it into the routes using `Depends()`. This allows FastAPI to automatically provide each route with a working SQLAlchemy Session when the route is called.

I also improved my understanding of why `yield` is used inside the database Session dependency. The purpose is not simply to allow the program to continue running. The important reason is that `yield` allows the Session to be temporarily passed to the route, and once the route finishes, execution returns to the dependency so the Session can be properly closed. This gives the Session a clear lifecycle for each request and prevents database connections from being left open unnecessarily.

I then converted the task retrieval logic from the old in-memory list approach to real database queries. Instead of looping through a Python list, I used SQLAlchemy's `select()` statement to query the `Task` table. I used `session.scalars(statement).all()` when I expected multiple task objects and `session.scalar(statement)` when I expected a single task.

I created a database-backed `GET /tasks` endpoint that retrieves task records directly from SQLite. This means that when the endpoint is called, FastAPI asks SQLAlchemy to query the database rather than reading from temporary application memory. I also learned the importance of using clear variable names such as `tasks` when multiple records are returned instead of using singular names such as `task`.

I also created a database-backed `POST /tasks` endpoint. Incoming JSON data is first validated by the Pydantic request model. After validation, the data is used to create a SQLAlchemy `Task` ORM object. I then used `session.add()` to tell the Session that the new task should be inserted, `session.commit()` to permanently save the transaction to SQLite, and `session.refresh()` to reload the object with values generated by the database, such as its primary-key ID.

An important improvement compared with my previous API was that I no longer need to manually generate task IDs. Previously, when working with a Python list, I had to calculate the next available ID myself. With SQLite and SQLAlchemy, the database handles primary-key generation automatically. This makes the system safer and removes unnecessary application logic.

I also created a database-backed endpoint for retrieving a single task by its ID. I used `select(Task).where(Task.id == task_id)` and executed the query using `session.scalar()`. I learned that when SQLAlchemy cannot find a matching row, `session.scalar()` returns `None`. It does not directly return a "Not Found" response. My FastAPI application is responsible for detecting the `None` value and raising an `HTTPException` with a `404 Not Found` status code.

I also worked on database filtering. I created a high-priority task query using `Task.priority >= 4`. Instead of retrieving every task from the database and filtering them using Python, I allowed SQLite to perform the filtering directly using the SQL query. This is more efficient because the application only receives the records that it actually needs.

I learned why database-side filtering becomes very important as systems grow. If a database contained hundreds of thousands or millions of records, loading every row into Python just to filter a few matching results would waste memory, network bandwidth and application processing time. Letting the database perform the filtering allows it to use its query engine and database indexes, making the application more efficient and scalable.

I also worked with FastAPI route ordering. Fixed routes such as a high-priority task endpoint should appear before dynamic routes such as `/tasks/{task_id}`. This prevents FastAPI from incorrectly interpreting a fixed route name as a dynamic task ID.

Another important task today was testing persistence. I created a task using the API, stopped the FastAPI server, restarted it, and queried the tasks again. The task was still available. This demonstrated the main advantage of replacing the Python list with SQLite. The task data is now stored on disk inside the database rather than only existing in application memory.

I also corrected my understanding of the roles of SQLAlchemy and SQLite. SQLite is the actual database system responsible for storing the task data. SQLAlchemy does not itself store the data. Instead, SQLAlchemy acts as the ORM and database access layer that allows the Python application to communicate with SQLite using Python objects and queries.

I attempted the optional `min_priority` query parameter challenge as well. My first implementation created a separate `/tasks/min_priority` route, but I learned that the better API design is to make `min_priority` an optional query parameter on the existing `/tasks` endpoint. This means the API can support requests such as `GET /tasks` to return all tasks and `GET /tasks?min_priority=4` to return only tasks with a priority of 4 or higher.

I also learned that an optional query parameter should use a value such as `None` when it is not provided. This allows the route to decide whether it should apply the filter or simply return every record. I also corrected the comparison from `Task.priority == min_priority` to `Task.priority >= min_priority`, because "minimum priority 4" should include both priority 4 and priority 5 rather than only tasks with exactly priority 4.

Overall, today's work brought together several topics from previous lessons. I combined FastAPI routing, Pydantic validation, dependency injection, HTTP error handling, SQLAlchemy ORM models, database Sessions, SELECT queries, filtering, commits, refreshes and SQLite persistence into one working database-backed API. The application has now moved from a basic temporary CRUD API toward a more realistic backend architecture where HTTP requests are validated by Pydantic, processed through FastAPI, handled using SQLAlchemy, and persisted inside a relational database.
