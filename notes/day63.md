## 2. What Is a Database Migration?

A database migration is a version-controlled set of changes that updates a database schema over time.

For example, an application might initially have a `tasks` table containing:

- `id`
- `title`
- `owner_id`

Later, the application needs a `priority` column.

Instead of deleting the table and recreating it, a migration can add the new column while preserving existing records.

Migrations help keep database structure consistent across development, testing, and production environments.

## 3. SQLAlchemy Models vs. Alembic

### SQLAlchemy models

SQLAlchemy models describe the database structure expected by the application.

Example:

```python
class Task(Base):
    __tablename__ = "tasks"

    id: Mapped[int] = mapped_column(primary_key=True)
    title: Mapped[str]
    owner_id: Mapped[int] = mapped_column(
        ForeignKey("users.id")
    )
```

### Alembic migrations

Alembic manages changes between database schema versions.

It records migration operations in Python files and tracks which revisions have been applied.

### Important distinction

```python
Base.metadata.create_all(engine)
```

This creates missing tables based on the registered models. It does not automatically update existing tables whenever a model changes.

Alembic provides a controlled process for applying those changes.

## 4. Initialising Alembic

Install Alembic by adding it to `requirements.txt`:

```text
alembic
```

Install the project's dependencies:

```powershell
pip install -r requirements.txt
```

Initialise Alembic:

```powershell
alembic init migrations
```

This creates:

- `alembic.ini`: Alembic's configuration file.
- `migrations/env.py`: The migration environment configuration.
- `migrations/versions/`: The directory containing migration scripts.
- `migrations/script.py.mako`: The template used to generate migration scripts.

## 5. Configuring the Migration Database

For this exercise, the Alembic configuration points to a separate SQLite practice database:

```ini
sqlalchemy.url = sqlite:///./migration_practice.db
```

Using a separate practice database prevents the exercise from accidentally changing the existing application database.

Database configuration must be checked carefully because migrations can alter or remove data when their operations are destructive.

## 6. Connecting Alembic to SQLAlchemy Metadata

In `migrations/env.py`, configure the metadata used for migration autogeneration:

```python
from main import Base

target_metadata = Base.metadata
```

`Base.metadata` contains the registered table definitions from the SQLAlchemy models.

Alembic compares this metadata with the database schema to identify potential changes.

If the metadata is missing or does not include the relevant models, autogenerated migrations may be incomplete.

## 7. Generating and Applying the Initial Migration

Generate the migration:

```powershell
alembic revision --autogenerate -m "create users and tasks tables"
```

Inspect the generated file under `migrations/versions/`.

For an empty practice database, the migration should contain operations to create the `users` and `tasks` tables, including the foreign key relationship between them.

Apply the migration:

```powershell
alembic upgrade head
```

This applies migrations up to the latest available revision.

The generated migration should always be inspected before it is applied.

## 8. Adding a New Column

The next exercise modifies the `Task` model by adding a `priority` field:

```python
priority: Mapped[int] = mapped_column(
    default=3,
    server_default="3",
    nullable=False
)
```

The configuration means:

- `Mapped[int]`: The field is mapped as an integer.
- `default=3`: SQLAlchemy uses a Python-side default when appropriate.
- `server_default="3"`: The database supplies a default value when an insert does not provide one.
- `nullable=False`: The column cannot contain `NULL`.

The server-side default is useful when adding a non-nullable column to a table that might already contain rows.

Generate the second migration:

```powershell
alembic revision --autogenerate -m "add priority to tasks"
```

Inspect the generated migration to confirm that it adds the `priority` column rather than unnecessarily dropping and recreating the tables.

Apply the migration:

```powershell
alembic upgrade head
```

## 9. Useful Alembic Commands

| Command | Purpose |
|---|---|
| `alembic init migrations` | Creates the Alembic migration structure. |
| `alembic revision --autogenerate -m "message"` | Generates a migration based on detected schema differences. |
| `alembic upgrade head` | Applies migrations up to the latest revision. |
| `alembic current` | Displays the current database revision. |
| `alembic history` | Displays the migration revision history. |

### Generating vs. applying migrations

Generating a migration creates a Python file containing proposed schema operations.

Applying a migration executes those operations against the configured database.

These are separate steps. Generating a migration does not automatically change the database schema.

## 10. Migration Safety

Autogenerated migrations are helpful, but they are not guaranteed to be correct.

Before applying a migration, inspect:

- The `upgrade()` function.
- The `downgrade()` function.
- Table and column creation or deletion.
- Foreign key changes.
- Default values and nullability.
- Potential data loss.

A migration's `upgrade()` function applies the change. Its `downgrade()` function attempts to reverse that change.

Not every database change can be reversed without losing information. Always test migrations before applying them to production.

For production databases, take appropriate backups and follow a reviewed deployment process.

## 11. Removing Automatic Table Creation

The application initially used:

```python
Base.metadata.create_all(engine)
```

For this migration exercise, automatic table creation was removed so that Alembic could manage schema creation and subsequent changes.

Removing this line does not itself delete existing database tables or records.

Alembic should become the explicit mechanism for managing schema changes in the application.

## 12. Answers to the Knowledge Check

**1. What problem does Alembic solve that `create_all()` does not?**

Alembic manages versioned schema changes, including changes to existing tables. `create_all()` primarily creates missing tables.

**2. What is the difference between generating and applying a migration?**

Generating creates a migration script. Applying executes the migration against the configured database.

**3. Why must `target_metadata` point to `Base.metadata`?**

It allows Alembic to inspect the SQLAlchemy models and compare their table definitions with the database schema.

**4. Why use a separate practice database?**

It isolates experimental schema changes from the existing application database and reduces the risk of accidental data loss.

**5. What does `alembic upgrade head` do?**

It applies pending migrations up to the latest revision in the migration history.

**6. Why inspect autogenerated migrations?**

Autogeneration may miss changes or produce operations that are inappropriate or destructive. Reviewing the script helps catch these problems before execution.

**7. What is `downgrade()` for?**

It defines how to reverse a migration when rolling back to an earlier schema revision, where reversal is possible.
