# Day 64: Database Rollbacks & Safe Schema Changes

## 1. Overview

Database migrations allow us to change a database schema as an application evolves.

However, changing a database is not just about adding or removing columns. We must also consider:

- Existing records in the database.
- Whether existing data remains valid after a change.
- How to reverse a migration when necessary.
- How to introduce required columns without breaking existing records.
- How SQLAlchemy defaults differ from database constraints.

This lesson covers migration history, rollbacks, nullable columns, backfilling data, and safer schema changes.

---

## 2. Understanding Alembic Migration History

Alembic tracks which database migrations have been applied.

### Check the current migration

```bash
alembic current
```

Shows the revision currently applied to the database configured in Alembic.

### View migration history

```bash
alembic history
```

Lists migration revisions and their relationships.

### View detailed migration history

```bash
alembic history --verbose
```

Displays additional information about migration revisions.

### Why migration history matters

Before rolling back or changing a database, you should know:

1. Which migration is currently applied.
2. Which migration came before it.
3. What changes each migration makes.
4. Whether reversing those changes could lose data.

## 3. Creating a Migration

Suppose the `Task` model currently has an `id`, `title`, `owner_id`, and `priority` column.

We want to introduce an optional `description` column.

### Update the SQLAlchemy model

```python
class Task(Base):
    __tablename__ = "tasks"

    id: Mapped[int] = mapped_column(primary_key=True)
    title: Mapped[str]
    owner_id: Mapped[int] = mapped_column(ForeignKey("users.id"))

    priority: Mapped[int] = mapped_column(
        default=3,
        server_default="3",
        nullable=False
    )

    description: Mapped[str | None] = mapped_column(
        nullable=True
    )
```

The `description` field is optional because its value can be `None`.

### Generate the migration

```bash
alembic revision --autogenerate -m "add task description"
```

Alembic compares the model metadata with the database schema and generates a proposed migration.

Autogenerated migrations must always be inspected before applying them.

### Apply the migration

```bash
alembic upgrade head
```

This applies outstanding migrations up to the latest revision.

---

## 4. Understanding the Migration File

A migration typically contains two functions.

### The `upgrade()` function

This applies the change.

For example:

```python
def upgrade() -> None:
    op.add_column(
        "tasks",
        sa.Column(
            "description",
            sa.String(),
            nullable=True
        )
    )
```

This adds a nullable `description` column to the `tasks` table.

Existing records can have `NULL` in the new column.

### The `downgrade()` function

This reverses the migration.

```python
def downgrade() -> None:
    op.drop_column("tasks", "description")
```

This removes the `description` column.

**Important:** Dropping a column also removes the data stored in that column. A downgrade can therefore cause data loss.

---

## 5. Rolling Back a Migration

Suppose you have applied a migration that adds the `description` column.

### Step 1: Check the current revision

```bash
alembic current
```

### Step 2: Roll back one revision

```bash
alembic downgrade -1
```

This moves the database back one revision by running the current migration's `downgrade()` function.

### Step 3: Check the revision again

```bash
alembic current
```

Confirm that the database is now at the expected previous revision.

### Step 4: Reapply the migration

```bash
alembic upgrade head
```

### Step 5: Verify the result

```bash
alembic current
alembic history
```

Confirm that the latest revision has been applied again.

### Rollback safety rules

- Use a development or practice database for rollback exercises.
- Inspect the migration's `downgrade()` function before running it.
- Remember that dropped columns and tables may contain valuable data.
- Do not run `alembic downgrade base` casually, because it attempts to reverse the migration history back to the base revision.
- A rollback changes the database schema and does not automatically restore data that was deleted or overwritten.
- In production, rolling back application code and rolling back database changes are separate concerns.

## 6. Understanding `nullable`

The `nullable` option controls whether a database column can contain SQL `NULL`.

### Nullable column

```python
description: Mapped[str | None] = mapped_column(
    nullable=True
)
```

The database allows the description to be missing.

For example:

```text
id | title             | description
---|-------------------|------------
1  | Learn SQLAlchemy  | NULL
2  | Build a Task API  | Practise CRUD
```

The first task has no description, which is permitted.

### Non-nullable column

```python
priority: Mapped[int] = mapped_column(
    nullable=False
)
```

The database requires every stored task to have a priority value.

`NULL` is not allowed.

Remember that `NULL` is different from:

- `0`, which is a numeric value.
- `""`, which is an empty string.
- `"3"`, which is text representing a number.

A non-null constraint does not automatically validate business rules such as whether a priority must be between 1 and 5. That requires an appropriate validation rule or database constraint.

## 7. Understanding `default`, `server_default`, and `nullable=False`

Consider this model field:

```python
priority: Mapped[int] = mapped_column(
    default=3,
    server_default="3",
    nullable=False
)
```

Each argument has a different purpose.

### `default=3`

This is a SQLAlchemy-side default.

When a new record is inserted through SQLAlchemy and the value is omitted, SQLAlchemy can supply `3`.

### `server_default="3"`

This defines a default at the database level.

When an SQL insert omits the `priority` column, the database can supply `3` automatically.

### `nullable=False`

This tells the database that the column must not contain `NULL`.

The database rejects an insert or update that attempts to store `NULL` in that column.

### Example: Omitting the priority

```python
new_task = Task(
    title="Learn migrations",
    owner_id=1
)
```

Because `priority` is omitted, the SQLAlchemy default can supply `3` when the record is inserted.

### Example: Explicitly providing `None`

```python
new_task = Task(
    title="Learn migrations",
    owner_id=1,
    priority=None
)
```

This explicitly supplies `None` rather than omitting the field. It does not mean "use the default."

When SQLAlchemy attempts to insert `NULL`, the database's `NOT NULL` constraint will reject it.

### Important distinction

Defaults and constraints solve different problems:

- A default provides a value when a value is omitted.
- A non-null constraint prevents the stored value from being `NULL`.

Adding a default does not mean the database should accept explicitly supplied `NULL` values.

## 8. What Is Database Backfilling?

**Backfilling is the process of populating existing database records with values after a schema or data requirement changes.**

Suppose your `tasks` table already contains 100 records.

You decide that every task needs a `priority` column, with existing tasks assigned priority `3`.

Those 100 existing records need values in the new column.

That data-population step is backfilling.

### Why backfilling matters

Adding a required column to an existing table can fail if the existing records cannot satisfy the new constraint.

For example, adding a non-nullable column without a suitable default may leave existing records without valid values.

A safer general process is:

1. Add the new column as nullable.
2. Backfill existing records.
3. Verify that the backfill succeeded.
4. Enforce `NOT NULL`.

### Step 1: Add the column as nullable

```python
def upgrade() -> None:
    op.add_column(
        "tasks",
        sa.Column(
            "priority",
            sa.Integer(),
            nullable=True
        )
    )
```

The column temporarily allows `NULL`.

### Step 2: Backfill existing records

```python
op.execute(
    "UPDATE tasks "
    "SET priority = 3 "
    "WHERE priority IS NULL"
)
```

This SQL statement updates existing tasks whose priority is missing.

The condition `WHERE priority IS NULL` ensures that existing non-null priority values are preserved.

### Step 3: Verify the backfill

```python
op.execute(
    "SELECT COUNT(*) "
    "FROM tasks "
    "WHERE priority IS NULL"
)
```

This query checks how many records still have a missing priority.

Run the query in your SQL client or database inspection tool and confirm the result is zero before enforcing the constraint.

### Step 4: Enforce `NOT NULL`

For a database such as PostgreSQL:

```python
op.alter_column(
    "tasks",
    "priority",
    existing_type=sa.Integer(),
    nullable=False
)
```

This changes the column so it no longer accepts `NULL`.

**SQLite note:** SQLite has limitations around altering existing column constraints. Alembic's `batch_alter_table()` may be required to implement the constraint change safely.

**Production note:** For large tables or high-traffic applications, adding the column, backfilling, and enforcing the constraint may need to happen across separate deployments to avoid long locks or downtime.

---

## 9. Why You Should Not Always Backfill

Backfilling is only necessary when existing records need values to satisfy the new requirement.

For example, adding this optional field:

```python
description: Mapped[str | None] = mapped_column(
    nullable=True
)
```

does not require a backfill if existing tasks are allowed to have no description.

By contrast, if every task must have a priority, the existing records need valid priority values before a non-null constraint can safely be enforced.

The correct approach depends on the requirements of the field and the data already stored.

## 10. Alembic and SQLAlchemy Responsibilities

| Component | Responsibility |
|---|---|
| SQLAlchemy model | Describes the intended application-side data structure. |
| Alembic revision | Records the schema changes to apply or reverse. |
| `upgrade()` | Applies the migration. |
| `downgrade()` | Attempts to reverse the migration. |
| `default` | Supplies a SQLAlchemy-side default during inserts. |
| `server_default` | Defines a database-side default. |
| `nullable=False` | Prevents `NULL` values in the database column. |
| Backfill SQL | Populates existing records with appropriate values. |

One crucial rule: **changing your SQLAlchemy model does not automatically update an existing database schema.** Use an Alembic migration to apply the change.

Also, `Base.metadata.create_all()` creates missing tables but is not a replacement for migrations that evolve existing tables. Once you adopt Alembic for schema management, keep the migration history as the source of truth for schema changes.

## Key Takeaways

1. Migrations let you evolve a database schema while keeping changes traceable.
2. Every migration should be inspected before it is applied.
3. Rollbacks can remove data, so they must be used carefully.
4. `nullable=False` prevents the database from storing `NULL` in a column.
5. `default` and `server_default` can provide values when a column is omitted, but explicit `NULL` is different.
6. Backfilling populates existing records with values required by a new schema or business rule.
7. A safe general sequence for a newly required column is: add nullable, backfill, verify, enforce non-null.
8. SQLite and PostgreSQL differ in some schema-alteration operations, so migrations should be tested against the database engine you actually use.
