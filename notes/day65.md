# Day 65: Production-Safe Database Migrations

## 1. Overview

Database migrations allow us to change a database schema as an application evolves. However, in a deployed application, database changes must be coordinated with application code to avoid breaking existing functionality.

This lesson covers:

- Production-safe schema changes.
- The expand/contract migration pattern.
- Backfilling existing records.
- Backward compatibility during deployments.
- Migration verification.
- Common Alembic configuration errors.

## 2. Why Production-Safe Migrations Matter

Suppose an application has a `tasks` table containing:

| id | title | description |
|---:|---|---|
| 1 | Learn FastAPI | Practise API development |
| 2 | Learn SQL | NULL |

We decide to rename `description` to `details`.

If we immediately remove or rename `description`, an older version of the application may still query that column. Those requests could fail because the database schema no longer matches what the application expects.

The solution is to introduce schema changes gradually while maintaining compatibility.

**Key principle:** A database migration must account for existing data and application versions that may still be running.

## 3. The Expand/Contract Pattern

Expand/contract is a strategy for introducing breaking database changes safely.

### Phase 1: Expand

Introduce the new schema while keeping the old schema available.

For our example:

- Keep `description`.
- Add `details`.
- Backfill existing values from `description` into `details`.

At this stage, both columns exist.

### Phase 2: Transition

Update the application to use `details`.

During a rolling deployment, older application instances may still depend on `description`. The transition must account for this.

Depending on the application, temporary dual-writing or compatibility logic may be needed so that both columns remain consistent while old and new versions coexist.

### Phase 3: Contract

After confirming that no application code depends on `description`, remove the old column in a separate migration.

```python
def upgrade() -> None:
    op.drop_column("tasks", "description")
```

Dropping a column removes the data stored in it, so this must not happen until the old column is no longer needed.

### Summary

1. Expand: add the new column.
2. Backfill: copy existing data.
3. Transition: update application code safely.
4. Verify: confirm the new version works and the old column is no longer needed.
5. Contract: remove the old column in a later migration.

## 4. Practical Example: Adding `details`

Assume the existing `description` column is already present in the database.

### Step 1: Update the SQLAlchemy model

Keep the old column and introduce the new one.

```python
description: Mapped[str | None] = mapped_column(
    nullable=True
)

details: Mapped[str | None] = mapped_column(
    nullable=True
)
```

Do not remove `description` during the expand phase.

### Step 2: Generate the migration

```bash
alembic revision --autogenerate -m "add task details column"
```

Alembic compares the model metadata with the current database schema and generates a proposed migration.

Autogenerated migrations should always be inspected before application.

### Step 3: Implement the backfill

The migration's `upgrade()` function can add the new column and copy the old values.

```python
def upgrade() -> None:
    op.add_column(
        "tasks",
        sa.Column(
            "details",
            sa.String(),
            nullable=True
        )
    )

    op.execute(
        "UPDATE tasks "
        "SET details = description "
        "WHERE details IS NULL "
        "AND description IS NOT NULL"
    )
```

The SQL copies existing non-null descriptions into `details`.

The conditions ensure that:
- Records with a missing description are not given an invented value.
- Existing non-null values in `details` are not overwritten.

This migration assumes the `description` column already exists.

### Step 4: Inspect the downgrade

The reverse operation should remove the newly added column.

```python
def downgrade() -> None:
    op.drop_column("tasks", "details")
```

**Important:** This downgrade removes any data stored in `details`. It does not automatically reconstruct the original data if other operations have changed or removed it.

### Step 5: Apply the migration

```bash
alembic current
alembic upgrade head
alembic current
```

The first command checks the current revision, the second applies outstanding migrations, and the third confirms the resulting revision.

Always check the target database before applying migrations.

## 5. Verifying the Backfill

After applying the migration, we need to confirm that the new column contains the expected data.

### Query 1: Inspect the values

```sql
SELECT id, description, details
FROM tasks;
```

This lets us compare the old and new columns.

For existing records with a non-null description, `details` should contain the copied value after the backfill.

### Query 2: Find records that were not backfilled

```sql
SELECT COUNT(*)
FROM tasks
WHERE description IS NOT NULL
  AND details IS NULL;
```

The expected result is `0`, assuming the backfill succeeded and no subsequent operation changed the data.

If the database contains no task records, insert test records before evaluating the result.

### Why verification matters

A migration completing successfully does not, by itself, prove that the data was transformed correctly.

Verification checks the actual database state rather than relying solely on the migration's success message.

## 6. Running SQL Against SQLite

Our practice configuration uses:

```ini
sqlalchemy.url = sqlite:///./migration_practice.db
```

This points Alembic to the practice SQLite database, with the relative path resolved from the application's working directory.

We can run the verification queries through a SQLite client or a Python script.

Example `check_migration.py`:

```python
import sqlite3

connection = sqlite3.connect("migration_practice.db")

try:
    rows = connection.execute("""
        SELECT id, description, details
        FROM tasks;
    """).fetchall()

    print("=== Task descriptions and details ===")

    for row in rows:
        print(row)

    result = connection.execute("""
        SELECT COUNT(*)
        FROM tasks
        WHERE description IS NOT NULL
          AND details IS NULL;
    """).fetchone()

    print("\n=== Backfill verification ===")
    print("Records missing details:", result[0])

finally:
    connection.close()
```

Run it from the directory containing the practice database:

```bash
python check_migration.py
```

The output depends on the records in the database.

### Important distinction

The SQL queries belong in a SQL client or a Python script. They must not be pasted into `alembic.ini`.

`alembic.ini` is a configuration file, not a SQL execution script.

## 7. Understanding `alembic.ini`

Our practice configuration contains:

```ini
[alembic]
script_location = %(here)s/migrations
prepend_sys_path = .
sqlalchemy.url = sqlite:///./migration_practice.db
```

### `script_location`

```ini
script_location = %(here)s/migrations
```

Specifies where Alembic stores and finds its migration scripts.

### `prepend_sys_path`

```ini
prepend_sys_path = .
```

Adds the current project directory to Python's import path so project modules can be imported.

### `sqlalchemy.url`

```ini
sqlalchemy.url = sqlite:///./migration_practice.db
```

Specifies the database URL used by the Alembic environment when configured to read it from this setting.

The project’s `migrations/env.py` can override this URL, so inspect that file if migrations appear to target a different database.

## 8. Debugging the `configparser.ParsingError`

During this lesson, Alembic returned an error similar to:

```text
configparser.ParsingError: Source contains parsing errors: 'alembic.ini'
```

The error listed lines containing:

```text
SELECT id, description, details
FROM tasks;
```

and the second SQL query.

### Cause

The SQL statements had been pasted into `alembic.ini`.

Python's configuration parser could not interpret those lines as valid configuration entries.

The migration had not necessarily failed. Alembic was failing while reading its configuration, before it could perform the requested migration.

### Fix

1. Open `alembic.ini`.
2. Remove the SQL statements accidentally pasted into it.
3. Preserve the existing Alembic configuration.
4. Save the file.
5. Rerun the Alembic commands.

```bash
alembic current
alembic upgrade head
alembic current
```

If the upgrade fails again, inspect the new error separately. A configuration parsing error and a database migration error are different problems.

### General debugging lesson

When an error occurs, identify the stage at which the failure happened.

For example:

- Configuration parsing errors occur while loading settings.
- Import errors occur when Python cannot load required modules.
- Migration errors occur while generating or executing schema changes.
- Verification errors occur when queries cannot run or the resulting data is incorrect.

Correctly identifying the stage makes debugging faster.

## 9. Backward Compatibility During Deployment

Backward compatibility means that a new database schema continues to support application versions that may still be running.

For example, during a rolling deployment:

- Old application instances may query `description`.
- New application instances may query `details`.
- Both versions might temporarily access the same database.

Removing `description` too early can break old instances.

A safe migration strategy keeps both columns available until the transition is complete.

For data that changes during this period, consider whether writes to both columns must remain synchronized. A one-time backfill copies existing values but does not automatically synchronize future writes.

## 10. SQLite and PostgreSQL Differences

SQLite and PostgreSQL support many of the same basic migration operations, but their schema-alteration capabilities differ.

For example, altering an existing column's nullability may require Alembic's `batch_alter_table()` when using SQLite.

PostgreSQL supports direct operations such as:

```python
op.alter_column(
    "tasks",
    "priority",
    existing_type=sa.Integer(),
    nullable=False
)
```

Always test migrations against the database engine used by the deployed application.

A migration that works on SQLite should not automatically be assumed to behave identically on PostgreSQL.

## 11. Production Safety Checklist

Before deploying a schema change:

- [ ] Confirm the target database.
- [ ] Inspect the generated migration.
- [ ] Consider the existing records and their values.
- [ ] Backfill data when required.
- [ ] Verify the backfill.
- [ ] Preserve compatibility with running application versions.
- [ ] Test the migration against the intended database engine.
- [ ] Review the downgrade for possible data loss.
- [ ] Remove old columns only after the application no longer depends on them.
- [ ] Keep production credentials and environment secrets out of Git.

## Key Takeaways

1. Production-safe migrations account for existing data and deployed application versions.
2. Expand/contract introduces changes gradually instead of removing old structures immediately.
3. Backfilling copies or calculates values for existing records; it does not automatically synchronize future writes.
4. A successful migration should be followed by data verification.
5. `alembic.ini` stores configuration, not SQL queries.
6. The migration environment determines which database Alembic actually uses.
7. Dropping a column can permanently remove data.
8. Test migrations against the intended database engine before production deployment.
